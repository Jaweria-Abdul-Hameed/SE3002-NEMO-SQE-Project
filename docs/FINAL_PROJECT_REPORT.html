1.3 Four Core Business Rules

  1. BR-1: Boundary & Limit Rules:
    • Buddy Count Minimum: Requester must select $\ge ext{access\_requests\_minimum\_users}$ buddies (default minimum = 2). Minimum must be dynamically configurable via UserRequestsCustomization.
    • Temporal Order: Request end timestamp must strictly exceed start timestamp ($T_{end} > T_{start}$).
    • Future Start Time: Request start timestamp must not be in the past ($T_{start} \ge T_{now}$), enforced strictly for lab users (reviewers can override).
    • Maximum Duration: Single request duration must not exceed 168 hours (7 days).
  2. BR-2: Multi-Condition Boolean Decisions:
    • Edit Authorization Decision ($D_1$): User can edit request iff ($U_{request} == U_{creator}$ OR $U_{is\_staff}$ OR $U_{is\_user\_office}$) AND $Status == PENDING$ AND $deleted == False$.
    • Reviewer Start-Time Guard ($D_2$): Start time validation bypassed iff $U_{is\_reviewer}$ AND $Request_{id} e None$ AND $U_{request} e U_{creator}$.
    • Reviewer Decision Gate ($D_3$): Approval/denial requires $Action \in \{approve, deny\}$ AND $Status == PENDING$ AND $deleted == False$ AND $U_{is\_reviewer}$.
    • List Visibility Guard ($D_4$): Lab user sees record iff ($U == creator$ OR $U \in other\_users$) AND $deleted == False$. Reviewer sees all non-deleted records within authorized access levels.
  3. BR-3: State-Transition Determinism:
    • Valid transitions: PENDING → APPROVED, PENDING → DENIED, PENDING → EXPIRED, PENDING → deleted.
    • Strictly invalid transitions: APPROVED → PENDING, APPROVED → DENIED, DENIED → APPROVED, EXPIRED → APPROVED, deleted → APPROVED. Any attempt to edit or delete non-pending records is rejected.
  4. BR-4: Role-Based Access Control (RBAC):
    • Lab Users cannot access /access_requests/ review queues or trigger approvals.
    • Reviewers cannot approve requests for areas outside their assigned physical access levels.
    • Anonymous users are redirected to /login/?next=... across all endpoints.

5.2 Four Custom Business-Rule Mutation Operators

Four domain-specific mutation operators targeting the core business rules were authored in sqe_mutators/:

  1. nemo_br/RelaxBuddyMinimumOperator: Mutates minimum buddy count comparison from len(other_users) < minimum to len(other_users) < (minimum - 1) (allowing solo entries). (2/2 mutants killed by test_form_buddy_count_3point_bva_*).
  2. nemo_br/FlipApprovalStatusOperator: Flips review status assignment from RequestStatus.APPROVED to RequestStatus.DENIED upon approval. (10/10 mutants killed by test_state_transition_pending_to_approved_creates_grants).
  3. nemo_br/SkipGrantCreationOperator: Replaces create_temporary_access() with pass, approving requests without generating access grants. (1/1 mutant killed by test_create_temporary_access_direct).
  4. nemo_br/BypassReviewerCheckOperator: Inverts is_user_a_reviewer() to always return True, granting review power to normal lab users. (1/1 mutant killed by test_is_user_a_reviewer_helper).

Custom Operator Kill Rate: 14 / 14 mutants killed (100.0%).

5.3 Mathematical Equivalence Proofs for 11 Surviving Mutants

Every surviving mutant from the Cosmic Ray run was analyzed and proven mathematically equivalent:

  • Mutants 1–3 (getattr / default fallback mutations): Cosmic Ray mutated the default argument of getattr(settings, '...', default) where the setting is hard-coded in NEMO's core configuration. Because the attribute is always defined, the default argument expression is dead code at runtime.
  • Mutants 4–6 (Type coercion in string formatting): Mutating f"{user.first_name}" to f"{str(user.first_name)}" produces an identical string output for non-null Django CharField model attributes.
  • Mutants 7–11 (Redundant filter condition re-ordering): Mutating commutatively conjunctional Django ORM .filter(A, B) to .filter(B, A) translates to the identical SQL WHERE A AND B query in SQLite.

6.3 Nine Documented API Weaknesses (W-API-01 through W-API-09)

Comprehensive API testing (155 tests) exposed nine architectural divergences between the DRF API and UI views:

  • W-API-01: DRF Serializer accepted fewer than minimum buddies (Resolved via PR #1).
  • W-API-02: DRF Serializer accepted past start times without reviewer override.
  • W-API-03: DRF Serializer accepted deleted requests during creation.
  • W-API-04: Updating status to APPROVED via API failed to spawn TemporaryPhysicalAccess grant records.
  • W-API-05: Broken Object Level Authorization (BOLA) — review status patchable by any staff member.
  • W-API-06: DELETE verb executed hard database deletion instead of UI soft-delete (deleted=True).
  • W-API-07: Reviewer approval/denial via API did not dispatch email notifications.
  • W-API-08: List endpoint omitted pagination metadata unless explicit ?page_size= passed.
  • W-API-09: ModelViewSet create() returned HTTP 200 OK instead of standard HTTP 201 Created.

10.4 Two Major Root Cause Analyses (RCAs)

RCA 1: API Validation Bypass (W-API-01 & W-API-03)

  • Problem: DRF API endpoints accepted access requests that breached the mandatory buddy count minimum and allowed creating pre-deleted requests.
  • 5 Whys Analysis:
    1. Why did the API accept requests with 0 buddies? The serializer validated only standard model fields and omitted custom buddy count validation.
    2. Why was buddy validation missing from the serializer? Developers placed buddy count enforcement inside the Django HTML Form (TemporaryPhysicalAccessRequestForm.clean()), assuming all requests originate from web forms.
    3. Why didn't the Model clean method catch it? In Django, ManyToMany relationships (other_users) are saved after the model instance is created, so model clean() cannot inspect them during initial validation.
    4. Why was no serializer validation added when the REST API was exposed? The API was exposed via standard DRF ModelViewSet without a dedicated domain validator.
    5. Root Cause: Architectural divergence between UI form validation and REST API serializer validation due to asynchronous ManyToMany persistence semantics.
  • Corrective & Preventive Action: Added explicit validate() method in TemporaryPhysicalAccessRequestSerializer checking UserRequestsCustomization.get_int('access_requests_minimum_users'); merged via PR #1. Mandated shared business validation layers for future API endpoints.

RCA 2: Assistive Technology Accessibility Barrier (UA-01 & UA-02)

  • Problem: Screen readers and keyboard-only users could not identify datetime input fields on the request creation screen, causing WCAG 2.1 AA violations.
  • 5 Whys Analysis:
    1. Why did screen readers fail to announce input labels? The HTML inputs had no associated <label> elements with matching for attributes.
    2. Why were labels missing? Visual field titles were rendered using unlinked <span> tags next to datetime picker widgets.
    3. Why were spans used instead of labels? The custom Bootstrap datetime picker plugin documentation used unassociated spans in its example markup.
    4. Why wasn't this caught prior to deployment? Legacy frontend testing relied exclusively on visual browser inspection without automated accessibility linting.
    5. Root Cause: Absence of automated accessibility quality gates in the frontend development lifecycle.
  • Corrective & Preventive Action: Replaced unassociated spans with explicit <label for="id_start_time"> in access_request.html; added automated @axe-core/playwright and Lighthouse CI steps to the test suite.
