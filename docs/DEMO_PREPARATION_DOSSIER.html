3. The 11-Step Data Lifecycle & Dual-Channel Architecture [SYSTEM ARCHITECTURE & CONTROL FLOW]

NEMO v8.2.1 operates a Dual-Channel Architecture: requests can enter through either the server-rendered Django Web UI or the Django REST Framework (DRF) HTTP API. Our quality engineering revealed a critical architectural discrepancy: validation rules implemented in the UI form layer were bypassed by DRF endpoints!

[CHANNEL 1: Web UI Client] [CHANNEL 2: REST API Client] │ │ ▼ ▼ [1. GET/POST /create_access_request/] [2. POST/PATCH /api/temporary_physical_...] │ │ ▼ ▼ [3. View Level Auth & Decorators] [4. DRF DjangoModelPermissions] (@login_required, @require_http_methods) (view_, add_, change_ permissions) │ │ ▼ ▼ [5. Form Validation (forms.py)] [6. Serializer Validation (serializers.py)] (clean(): checks minimum buddy count (ORIGINAL GAP: fields="__all__" omitted access_requests_minimum_users - 1) buddy count validation! FIXED IN PR #1) │ │ ▼ ▼ [7. Domain Model Validation (models.py :: clean())] (Enforces end_time > start_time; raises ValidationError) │ ▼ [8. SQLite Persistent Transaction (sqe_nemo.db)] (Inserts TemporaryPhysicalAccessRequest in PENDING (0) state) │ ▼ [9. Reviewer Notification Creation (models.py)] (Inserts Notification row for facility managers / area reviewers) │ ▼ [10. Workflow 2 Review Decision (Approve / Deny)] (Reviewer POST with approve_request OR deny_request) ├── DENY: status -> 2 (DENIED), reviewer set, 0 grants created └── APPROVE: status -> 1 (APPROVED), reviewer set, create_temporary_access() creates N grant records │ ▼ [11. State Lock & Invalidation] (Subsequent edits or deletes rejected with 400 Bad Request; expired requests auto-transitioned to EXPIRED (3) on view load)
Core Architectural Discovery: The UI vs. API Validation Divergence

In monolithic web frameworks like Django, developers often place critical validation logic inside HTML form classes (TemporaryPhysicalAccessRequestForm.clean()) rather than in shared domain services or model managers.

When Django REST Framework serializers were subsequently introduced (TemporaryPhysicalAccessRequestSerializer), DRF bypassed forms.py completely. Furthermore, standard DRF ModelSerializer classes do not automatically call model.full_clean() unless explicitly invoked!

This architectural gap allowed external API clients to submit access requests with 0 buddies (violating BR-1), submit past start-times, and execute arbitrary state transitions (e.g. APPROVED -> PENDING via PATCH). Our team systematically caught this in Phase 4 (logged as W-API-01 through W-API-06) and delivered the production-ready architectural fix in PR #1.

7. The 4 Real Incidents & Live Debugging Breakthroughs [WAR STORIES & RESILIENCE]

Incident 1: The DRF `ModelSerializer` Silent Validation Omission Trap BACKEND ARCHITECTURE

The Symptom: During Phase 4 boundary testing, submitting a REST API request with other_users: [] (0 buddies) returned HTTP 200 OK and persisted an invalid request, even though the web UI rejected it with a clear error message.

The Root Cause: Developers assumed DRF's ModelSerializer with fields = "__all__" automatically inherits validation from Django's form class (TemporaryPhysicalAccessRequestForm.clean()). It does not! Furthermore, standard DRF serializers only invoke field-level model validation and omit cross-field model clean() unless explicitly programmed.

The Fix: In PR #1 (fix/w-api-01-buddy-count-serializer), we added a dedicated validate() method to TemporaryPhysicalAccessRequestSerializer in NEMO/serializers.py, enforcing len(other_users) + 1 >= min_users and returning HTTP 400 Bad Request.

Manifest / Code Fix: NEMO/serializers.py -> TemporaryPhysicalAccessRequestSerializer.validate()
Incident 2: The Cosmic Ray SQLite Multiprocessing Lock Contention TEST TOOLING

The Symptom: When running Cosmic Ray mutation testing in parallel across 162 mutants on Windows, worker processes crashed intermittently with: sqlite3.OperationalError: database is locked.

The Root Cause: SQLite default timeout is low (5 seconds), and Cosmic Ray worker processes concurrently wrote mutation execution results to cr_baseline.sqlite while Django tests simultaneously initialized in-memory/disk test databases.

The Fix: We engineered scripts/run_cosmic_ray_parallel.py with per-worker SQLite timeout flags (30s busy timeout), WAL mode (Write-Ahead Logging), and separated the custom forms mutation run into its own isolated session file cr_forms_custom.sqlite.

Tool Fix: scripts/run_cosmic_ray_parallel.py & scripts/run_custom_forms_mutation.py
Incident 3: The Playwright Bootstrap DateTimePicker Popover Focus Trap E2E AUTOMATION

The Symptom: In automated keyboard navigation test USA-WF1-ERR-KBD, pressing Tab after filling #start_time caused document.activeElement to become trapped in the date picker popover rather than advancing to #end_time and #description.

The Root Cause: The legacy Bootstrap DateTimePicker jQuery plugin intercepts focus and displays an active calendar table popup that absorbs sequential Tab events.

The Fix: Dispatched an explicit Escape keyboard event immediately after date input entry to cleanly dismiss the popover widget, allowing sequential Tab focus navigation to advance smoothly through all form inputs to the submit button.

Code Fix: tests/team/usability/usability_and_keyboard.spec.mjs -> page.keyboard.press('Escape')
Incident 4: The Dynamic Buddy Removal DOM Anchor Defect (`link-name`) ACCESSIBILITY

The Symptom: axe-core and Google Lighthouse audits flagged a Serious link-name accessibility violation on the access request creation and review screens.

The Root Cause: When a user dynamically added a buddy chip via JavaScript, the removal control was rendered as an anchor tag with no text content: <a href="javascript:void" onclick="remove_other_user(this)"><span class="glyphicon glyphicon-remove-circle"></span></a>. Screen readers announced "link, javascript:void" with no indication of what buddy would be removed.

The Fix: In NEMO/templates/requests/access_requests/access_request.html, we refactored the JavaScript DOM injection to create a semantic <button type="button" class="btn btn-default btn-xs" aria-label="Remove buddy {{ user.get_name }}"> with aria-hidden="true" on the glyphicon. Axe-core violations dropped from 4 to 1 and Lighthouse Accessibility rose from 86 to 91.

Template Fix: NEMO/templates/requests/access_requests/access_request.html:153

None represent executable bugs, giving an equivalent-adjusted mutation score of 100.0%.

Reference: docs/PHASE3_MUTATION_ANALYSIS.md (Section 4 Equivalence Proofs)
